# Export Aptos Verifier

[![dependency status](https://deps.rs/repo/github/mysteryon88/export-aptos-verifier/status.svg)](https://deps.rs/repo/github/mysteryon88/export-aptos-verifier)

**Export Aptos Verifier** is a CLI tool and Rust library for generating **Groth16** Aptos Move verifier packages.

It supports **BN254** and **BLS12-381** verification artifacts from **snarkjs**, **Gnark**, **SP1**, and **Arkworks**. Supported inputs include JSON, native Gnark binary files, SP1 Groth16 wrapper proofs, Arkworks JSON/hex files, and compact Arkworks bundles. The curve and input format are auto-detected.

When proof data is supplied, the tool verifies it locally and generates Move tests with the package. VK-only generation is also supported.

## Installation

```bash
cargo install export-aptos-verifier

# Help
export-aptos-verifier --help
```

## Import as a library

```bash
cargo add export-aptos-verifier-core
```

```rust
use export_aptos_verifier_core::{
    curves::create_adapter,
    formats::{
        load_compact_bundle, load_gnark_binary_inputs, load_gnark_json_inputs,
        load_snarkjs_json_inputs_with_optional_proof, load_sp1_groth16_inputs,
    },
    movegen::{generate_move_package, GenerateMovePackageOptions, MovegenMode},
};
```

Most users only need the CLI. Use the core crate when embedding verifier generation into another Rust tool.

## Usage CLI

```sh
# From snarkjs-compatible verification_key.json:
export-aptos-verifier --vk ./verification_key.json --out ./generated/verifier --force

# Include proof data for local verification and generated Move tests:
export-aptos-verifier --vk ./verification_key.json --proof ./proof.json --public ./public.json --out ./generated/verifier --force

# From native Gnark JSON or binary artifacts:
export-aptos-verifier --vk ./verification_key_gnark.json --proof ./proof_gnark.json --public ./public.json --out ./generated/gnark_verifier --force
export-aptos-verifier --vk ./verification_key.bin --proof ./proof.bin --public ./public.json --out ./generated/gnark_verifier --force

# From an SP1 Groth16 wrapper proof:
export-aptos-verifier --vk ./groth16_vk.bin --proof ./sp1_proof.bin --out ./generated/sp1_verifier --force

# From a compact Arkworks bundle:
export-aptos-verifier --bundle ./groth16_artifacts.json --out ./generated/arkworks_verifier --force

# Customize the generated Move package:
export-aptos-verifier --vk ./verification_key.json --out ./generated/verifier --package-name verifier --module-name verifier --account-address 0x0 --mode entry --force

# Generate proof helper functions or run Aptos Move tests:
export-aptos-verifier proof-data --vk ./verification_key.json --proof ./proof.json
export-aptos-verifier --vk ./verification_key.json --proof ./proof.json --out ./generated/verifier --run-aptos-test --force
```

`--package-name` is derived from `--out` by default. `--module-name` defaults to `verifier`, `--account-address` defaults to `0x0`, and `--mode` defaults to `entry`. Available modes are `library`, `entry`, and `test`.

## Security

Generated verification is stateless: a valid proof can be replayed unless the calling application uses persistent replay state. Bind a domain/version separator, unique nullifier, account, package, module, network/chain, operation, and expected verification-key or circuit identity into the circuit's public inputs. Recompute the same context in the consuming Move module, reject used nullifiers, and record a nullifier only after successful verification. See the [stateful gatekeeper example](./examples/stateful-gatekeeper/).

The verifier fingerprint identifies the embedded verification-key bytes and detects mismatch only when compared with a value obtained through a trusted channel. It proves neither verification-key or circuit provenance/authenticity nor an honest trusted setup, and does not replace review of the artifacts and generated code. Generated packages use an immutable upgrade policy; deploy a new verifier identity and migrate consumers explicitly for any change.

The CLI verifies proof-bearing inputs locally by default; core-library callers must invoke `local_verify` explicitly. VK-only generation and `--skip-local-verify` do not provide that check and require independent validation before deployment.

`--force` creates a missing or empty output directory, or replaces a directory previously generated by this tool and marked with its manifest. It refuses regular files, symlinks, and nonempty unmarked directories; a forced regeneration replaces the whole marked directory.

## Output directory safety

Generation rejects `..` before creating any parent and refuses filesystem roots, the current directory and its ancestors. Every existing path component must be a real directory, without symlinks or Windows reparse points. Windows output currently requires a local drive path; UNC/device paths are unsupported.

Output is written through retained directory handles into exclusive, private staging (Linux mode `0700`; Windows protected, inheritable owner/SYSTEM DACL). Files are created exclusively. Publication, force backup, rollback and cleanup use native operations relative to retained handles. Linux requires `renameat2(RENAME_NOREPLACE)`; Windows uses a held source handle and `FILE_RENAME_INFORMATION` with `ReplaceIfExists = FALSE`. Existing destinations, including raced empty directories, files and symlinks, are never replaced without force. An unsupported filesystem fails safely instead of falling back to a replacing rename. WSL DrvFS does not provide the required rename operation on the tested host; use a native Linux filesystem such as ext4 or run the Windows generator. Parsing remains available on other platforms, where generation returns `Unsupported`.

Force compares the target and actual backup against held cwd/ancestor directory identities, including alternate path spellings and aliases. It validates the actual directory moved to backup. A failed commit restores it only if the destination is still absent. If a concurrent destination prevents rollback, both it and the backup survive and the error reports the recovery location. Failed transactions retain staging for inspection; paths in errors are the last known locations and can become stale if an ancestor was renamed. Successful cleanup remains handle-relative and refuses unexpected symlinks or uncertain directory identities.

Aptos force additionally requires the complete current manifest, the requested package/module/account identity, the exact generated file inventory and matching SHA256 hashes. Extra files, modified generated files, nested symlinks and legacy manifests without file hashes are refused. To migrate older output or preserve application edits, generate into a new directory and review/migrate those edits explicitly. The public manifest is an accidental-deletion guard, not ownership authentication: use force only on a trusted output directory. An actor who can rewrite just the manifest and knows the existing contents can forge assertions for a matching allowed layout.

## Public scalar encodings

Arkworks and compact public inputs use the same grammar in JSON strings and raw scalar files: unprefixed digits are decimal at every length, `0x`/`0X` is a numeric big-endian hexadecimal integer, and `le:` followed by exactly 64 hex characters is one serialized 32-byte little-endian scalar. Bare 64-character hex containing `a-f` remains accepted for legacy byte artifacts; use `le:` for new serialized inputs so digit-only bytes cannot change meaning. Values must still fit the selected curve's scalar field.

The Arkworks MiMC producer writes the explicit `le:` marker in both `groth16_artifacts.json` and `public_input.hex`; VK/proof `.hex` files remain ordinary byte hex. JSON collection and aggregate structural limits are checked before allocating artifact trees, so oversized collections now fail at the JSON boundary.

High-level loaders validate point geometry, subgroup membership, scalar range and supported SP1 wrapper consistency. Groth16 pairing verification remains explicit via `local_verify` or the default CLI flow; `--skip-local-verify` skips only that equation check.

On Linux, each traversed parent must be owned by the effective UID or root and must have no group/other write permission unless sticky. Newly created directories must be effective-UID-owned and private. Untrusted owners and writable nonsticky traversal parents are rejected with `Unsupported`; this can reject WSL DrvFS before publication is attempted. This boundary excludes same-UID and privileged attackers. Parent trust is checked before opening each next component and before every directory creation; an unexpected newly opened object is preserved, without chmod/chown or deletion.
